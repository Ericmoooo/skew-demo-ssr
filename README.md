# Skew Demo: SSR Next.js Items + Contact

A Next.js 15 SSR app (App Router with RSC + Server Actions) that reproduces **deployment skew failures** on dynamic and server-rendered surfaces. Useful for demonstrating that platform-level skew protection (as implemented by Vercel and AWS Amplify Hosting) is necessary.

## What is deployment skew?

When a new version of an app is deployed, users with the old version's HTML loaded reference fingerprinted assets and Server Action endpoints that may have changed. Without skew protection, those references either 404 or return wrong-shape responses against the new deployment.

## Failure modes demonstrated

1. **Server Action POST**: form submit either 404s or returns a wrong field-shape response
2. **RSC payload drift**: prefetched server-rendered payload from the old build, new build's component code expects different field names
3. **Dynamic route navigation**: chunk 404 + RSC drift combined

## Reproduction

### Setup

```bash
npm install
NEXT_PUBLIC_BUILD_LABEL=A npm run build
npm run start
```

Open the deployed URL. Header should show "Build: A" on blue background.

### Trigger skew

In a separate terminal or after stopping the server:

```bash
NEXT_PUBLIC_BUILD_LABEL=B npm run build
npm run start
```

### Observe failures (DO NOT REFRESH the browser tab)

| Action | Expected failure |
|---|---|
| Submit the contact form on `/contact` | One of: (a) 404 in Network panel on the Server Action POST if the action id changed, (b) response with `caseRef` field that the form does not display, (c) `Failed to find Server Action` error in console |
| Click an item on `/` (prefetched link) | Item detail page renders with `(no name field)` because Build A's RSC payload used `name`, Build B's component code expects `displayName` |
| Reload `/items/alpha` directly | Loads from Build B with correct shape (this is the recovery path) |

### Recovery

Hard refresh. Build B loads cleanly. Form, items list, and item detail all work with B's contracts.

## Why each failure happens

### Server Action

When you write `"use server"` in a file like `app/contact/actions.ts`, Next.js compiles each exported function into an addressable RPC endpoint. The endpoint id is derived from the file path and the bundled content hash. Build A and Build B produce different ids. The form rendered by Build A's HTML contains a hidden `$ACTION_ID_<hash>` reference; submitting that form against Build B's server attempts to invoke an action id that may not exist.

### RSC payload drift

`next/link` prefetches the destination route's RSC payload (a serialized server-rendered tree) when the link enters the viewport or on hover. The prefetched payload was generated by Build A and embeds Build A's data shape. When the user clicks the link, Next's client router uses that prefetched payload to render Build B's component code, but the field names diverge. Result: silent missing-data renders or hydration errors.

### Chunk 404

Same as in the static demo: dynamic imports for nested routes have content-hashed chunk paths. Build A's HTML references chunks that don't exist at Build B's deployment.

## Field shape changes between builds (intentional)

| Surface | Build A | Build B |
|---|---|---|
| Items list `/` | `name` field | `displayName` field |
| Item detail `/items/[id]` | `id` field, `_shape: 'v1-original'` | `itemId` field, `_shape: 'v2-renamed'` |
| Contact action response | `ticketId` | `caseRef` |

These are exactly the kind of contract changes that happen between two real-world deployments. Skew protection ensures users on stale HTML continue to receive the OLD shape (because the gateway routes them to the OLD build's compute and assets).

## Deploy

After `next build`, the SSR app needs a Node runtime that runs `next start`.

```bash
npm install
NEXT_PUBLIC_BUILD_LABEL=A npm run build
npm run start
```
